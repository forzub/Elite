# Мешэдитор — спецификация (черновик для обсуждения с автором, 2026-11-13)

Статус: схема ПРИНЯТА автором 2026-11-13 («да, принимаю твою схему»). Окна 6.x/7.x уточняются с автором по одному.
Решения автора помечены «(автор)».

Умолчания, принятые вместе со схемой: статусы карточки — не обработана / в работе / готова / устарела; старые модели
показываются в «Открыть» как есть (статус «не обработана»), чистка источников — отдельно (MODEL_ASSET_STORAGE.md).

## 1. Зачем он нам

Работа с меш-моделями всех объектов игры:
- оборудования кораблей, станций и модулей хабов;
- кораблей;
- модулей станций и хабов, модулей модулей.

Вход — то, что сделано в Blender (автор) или сгенерировано скриптами (Claude). Выход — пакет модели, который **игра
реально читает**: LOD, хитвалумы, физика, элементы и их роли, состояния повреждений, гнёзда, анимация.

Главное требование к новому редактору: с первого среза его результат грузится в игру. Старый редактор умеет много, но
игра почти ничего из его выхода не читает:
- хиты, коллизии и повреждения `.elmodel` не используются;
- корабли каталога рисуются коробками;
- 116 моделей оборудования лежат без дела.

## 2. Переделывать или с нуля (предложение)

- **С нуля:** интерфейс и сценарий работы. Старый — один файл сессии на 12.8 тыс. строк, сжатая страница на 293 КБ;
  автор: «очень неудобно».
- **Переиспользовать проверенное ядро:**

## 3. Два вида моделей: деталь и сборка (автор: «использование ссылок выглядит очень разумно»)

- **Деталь** — оборудование, модуль хаба и т. п. Свой файл в собственных координатах:
  - LOD;
  - элементы и их роли;
  - хитвалумы;
  - физика (масса, центр масс, инерция);
  - состояния повреждений;
  - точки подключения (крепление, питание, данные);
  - анимация узлов.
- **Сборка** — корабль, станция, хаб, составной модуль:
  - свой корпус (рама + обшивка = «кожура»), его LOD, броня-хитвалумы, отсеки;
  - гнёзда со ссылками на детали (штатная комплектация).
  - Меши деталей в сборку не копируются.
- **Следствия:**
  - замена оборудования (F7) меняет только ссылку;
  - вдали рисуется корпус + крупные внешние детали, мелочь отсекается по экранному размеру;
  - попадание проходит броню корпуса, потом хитвалумы деталей внутри;
  - сборка может входить в сборку (модуль хаба в хабе).

Порядок работы (автор): «собираем сначала детали каждого с его собственной физикой, потом собираем ссылки в корабль на
раму и обтягиваем обшивкой».

- Кнопка «Открыть» → модальное окно с большими кнопками разделов:
  - оборудование кораблей;
  - корабли;
  - оборудование станций;
  - станции;
  - оборудование модулей хабов;
  - модули хабов.
- Раздел → карточки папок. На карточке:
  - снимок модели (редактор рендерит сам);
  - что это (из `asset.json`);
  - где используется — для какого корабля или хаба, по каталогу кораблей и данным хабов;
  - статус готовности: не обработана / в работе / готова / устарела (источник изменился после сборки).
- Над карточками — список «объект» (автор 2026-11-13: «кобра А3 — и будет только оборудование для этого корабля»):
  все корабли / станции / модули, где используется хоть одна модель раздела, с числом моделей; выбор оставляет только
  их. Отдельный пункт — «нигде не используется».
- Клик по карточке открывает модель. Сразу идёт проверка каждого элемента на годность к рендеру (шаг 6.1).

## 8. Изменения источника

- Элемент опознаётся **по имени**, не по номеру.
- При повторном импорте окно разницы: добавлено / удалено / изменено (отпечаток геометрии).
- **Удалён:** всё привязанное (хитвалум, состояния, отметки) становится «сиротами» — перепривязать или выбросить.
  Ничего не теряется молча.
- **Изменён:** его LOD и хитвалумы помечаются «устарело — проверить».
- **Добавлен:** ждёт роли в шаге 6.2.

## 9. Соглашение об именах (одно для Blender и для Claude)

- Элемент: `<имя>`, например `turret_barrel`.
- Состояния повреждения: `<имя>__damaged`, `<имя>__destroyed`.
- LOD внутри одного источника: `<имя>__lod1`, `__lod2` (если делаются вручную; иначе генерируются).
- Роль (необязательно, иначе назначается в 6.2): пользовательское свойство `elite_role` = `body` / `power` / `control` /
  `power_supply` / `control_supply`.
- Ссылка на деталь в сборке: пользовательское свойство `elite_part` = `<раздел>/<id>`.

## 10. Blender (автор: glTF подходит; «там же можно делать и скелетную анимацию»)

**Как работать:**
1. Детали — библиотека ассетов Blender: редактор выгружает готовые детали в библиотечный .blend; браузер ассетов
   Blender показывает их с превью.
2. В сцене корабля:
   - рама и обшивка — обычные меши;
   - детали — экземпляры коллекций из библиотеки (Link) с пометкой `elite_part`.
3. Экспорт: glTF, с «Custom Properties» (extras) и анимацией.
4. Импорт в редактор:
   - узел с `elite_part` → гнездо со ссылкой (его меши не берём);
   - остальное → корпус.
- Небольшое дополнение для Blender (Claude напишет): «поставить деталь из библиотеки», «пометить», «экспорт для Elite».

**Проверено 2026-11-13, Blender 5.0.1, без интерфейса** (`D:/tmp/gltf_test`, скрипт в черновиках сессии):
- Библиотека `parts_library.blend` (radar, turret — коллекции-ассеты). Сцена корабля: frame, skin, три экземпляра по
  ссылке (radar_top, turret_left, turret_right) с `elite_part`, ключи поворота на turret_left.
- В `ship.gltf`:
  - экземпляр — узел с именем, положением и поворотом, `extras: {"elite_part": "equipment_ship/turret"}` и детьми —
    мешами детали;
  - обе турели ссылаются на одни и те же меши (индексы 4 и 5) — копий нет;
  - анимация `turret_leftAction` — канал rotation узла экземпляра;
  - оси переведены в Y-вверх самим экспортёром.
- Вывод: всё нужное для гнёзд и анимации узлов в glTF доходит.

**Анимация:**
- для механики — анимация узлов (деталь движется целиком): турели, створки, опоры;
- скелетная анимация (кости + веса вершин) в glTF тоже есть — для того, что гнётся.

## 14. Скорлупы (трафик) — принято автором 2026-11-13 («да, переноси traf в shells»)

Автор: «трафик — дешёвые модели… чисто внешняя модель без каких-либо внутренних дополнений… скорлупы как организация
трафика и логистики — боты и НПС, когда они не в контакте с игроком; полноценным корабль становится только когда вступает
в контакт». В коде это уровни TrafficShell → MaterializedShip (`docs/SHIP_SIMULATION_TIER_TESTS.md`,
`docs/SHIP_STATE_CONTRACT.md`).

Хранение: скорлупа — в папке своего корабля, не в общей:

```
ships/cobrettymk1/
  LOD0/                 детали
  shells/<имя>/*.obj    скорлупы этого корабля (например traf: корпус + кабина)
  asset.json            "shells": {"traf": {"use": ["traffic"]}, ...}
```

`use`: `traffic` (трафик / логистика вне контакта), при желании ещё `lod` (вид издалека), `physics` (грубая форма).
Редактор уже показывает `shells/<имя>/` при открытии модели строкой «скорлупа <имя>».

## 17. Модуль в игре — скорлупа (обсуждено с автором 2026-11-14, ещё не сделано)

Автор: «модуль является объектом, который не вскрывается… нет смысла хранить полигоны под внешней оболочкой»;
«корабль — скелет, к нему прикреплены модули, которые могут от корабля отвалиться, но целиком».

- **Скорлупа** — это только поверхность, видимая снаружи: тонкие двусторонние листы без внутренней деталировки.
  Снаружи она полностью повторяет вид модели. Это не LOD: у скорлупы свои LOD.
- **Модуль в игре — всегда скорлупа.** Элементы генератора (например `fl_harness` под корпусом) — только исходник для
  её построения.
- **Корабль** — скелет (рама); к нему крепятся модули. Модуль отваливается **только целиком**, поэтому внутри модуля
  элементы по повреждениям не делятся.
- **Слияние:** в одну жёсткую оболочку сливаются элементы, которые движутся вместе. Неподвижный модуль (CR-1, лазер) —
  одна оболочка. Анимированный (складная лыжа, открывающийся контейнер, ремонтный робот) — по оболочке на подвижное
  звено, у каждой свой шарнир (точка, ось, пределы).
- **Видимость** проверяется во всех позах анимации: остаётся всё, что видно снаружи хотя бы в одной позе (внутренняя
  стенка открытого контейнера, ниша сложенной лыжи).
- **Хитвалумы элементов остаются** в физике (учёт попаданий внутри модуля), хотя сетка слита. Материалы остаются на
  треугольниках.
- **Скорлупа корабля** (трафик, раздел 14) считается по всей сборке: корпус закрывает части модулей, поэтому её нельзя
  сложить из скорлуп модулей.
- **Строит редактор** при сборке: лучи из многих направлений, остаются грани, в которые луч попадает первым.
  Проверка на CR-1 LOD0 (Blender, 500 направлений): видно снаружи не меньше 72% из 15 362 граней (оценка снизу).

Решения автора (2026-11-14):
- **Всё, из чего собирается корабль, — модули со своим id и паспортом**: оборудование, куски рамы, панели обшивки
  (обшивки в моделях пока нет). Корабль собирается по этим id.
- **Минимальный объект сборки — скорлупа.** Меш-редактор перегоняет элементарные модели в скорлупы и складывает их в
  библиотеку Blender; в сборке они ставятся ссылками и опознаются по id.
- **Повреждённый модуль — другая модель со своими LOD** (нет половины корпуса, сквозная дыра, открытый срез); она
  подставляется вместо целой. Скорлупа строится и для неё.

Решение за мной (автор: «тут тебе виднее»), звенья и шарниры:
- файл `rig.json` рядом с `hit_volumes.json`; его пишет генератор (или он приходит из Blender: иерархия объектов,
  начало объекта = шарнир, свойство `elite_joint`);
- содержимое: звенья (id, элементы, родитель), шарнир (точка, ось, вид hinge / slide, пределы), именованные позы
  (например `stowed` / `deployed`);
- нет файла — модуль одно жёсткое звено.

Хранение (предложение):
```
<раздел>/<id>/LOD<N>/*.obj            элементы (исходник)
<раздел>/<id>/damaged/<состояние>/LOD<N>/*.obj   повреждённые модели
<раздел>/<id>/rig.json, hit_volumes.json
assets/compiled/<раздел>/<id>/<id>.elmodel + .lod<N>.elmesh   пакет модуля (пишет редактор, 17.2)
assets/compiled/<раздел>/<id>/<id>.blend                     модуль для сборки в Blender
```

### 18.1 Раскладка

```
<раздел>/<id>/
  model.json                                паспорт (без него папка — не модель)
  intact/assembly/LOD<N>/                   сборка целой модели: генератор или Blender (.obj / .gltf)
  intact/assembly/hit_volumes.json, rig.json, assembly.json (документ редактора)
  intact/shell/LOD<N>/                      скорлупа (строит редактор; или ручная из Blender)
  damaged/<вариант>/assembly/LOD<N>/ …      повреждённый вариант: та же раскладка
  damaged/<вариант>/shell/LOD<N>/
```

- Сборка может сама быть скорлупой (панель обшивки, кусок рамы): тогда скорлупа не строится, а ссылается на сборку.
- У скорлупы — пометка `shell.json`: «построена из версии сборки …» или «ручная» (ручную редактор не перезаписывает,
  только предупреждает, если сборка новее).
- Пакет `.elmodel` собирается в `assets/compiled/<раздел>/<id>/` из всех вариантов.

### 18.2 Паспорт `model.json` (schema `elite.model.v1`)

`id`, `title`, `description`, `kind` (module / ship / station / hub_module / object), `variants`:
`[{id: "intact", title: "Целая", inGame: "shell" | "assembly+shell"}, {id: "<вариант>", title, inGame}]`.

### 18.3 Экран 1 (загрузка и проверка)

- Закладки — варианты: «Целая», затем повреждённые; закладка «+» добавляет вариант. Закладки остаются на всех
  следующих экранах.
- В закладке две секции, «Сборка» и «Скорлупа», у каждой свой ряд LOD0…LOD3.
- Выбор «В игру: сборка + скорлупа / только скорлупа» — у каждой закладки свой.
- Задача экрана: проверить, починить, по возможности упростить, найти повторы, построить скорлупу и LOD.
  Порядок: загрузка → проверка и починка → повторы → скорлупа и LOD (по разу на уникальную секцию).

### 18.4 Повторяющиеся секции

- Ищутся после починки (сравнение честное), до скорлупы и LOD (считаются один раз).
- Лучше всего повторы приходят из источника (ссылки в Blender, экземпляры генератора). Автопоиск — для слитых сеток:
  он только предлагает «эти N кусков одинаковы с точностью до 1 мм (с поворотом) — сделать одной секцией?».
- Скорлупа сегмента строится отдельно, с торцами: сегмент остаётся самостоятельным модулем (свалка, мастерская).
- Бублик: сегменты — модули, бублик — сборка из ссылок, сектора — группы разрушения с вариантами «цел / разрушен A / B»
  (узел-группа с состояниями; узлы отрисовки по состояниям). Сектора задаются заранее. Дальние LOD бублика — один
  слитый меш.

### 18.5 Сколько вариантов повреждения

- Одиночные модули: повреждён 1, разрушен 1.
- Повторяющиеся на корабле: повреждён 2–3, разрушен 1–2.
- Сегменты станций и сектора: 3.
- Разнообразие без новых моделей: поворот вокруг оси модуля, зеркало (если симметричен), случайный набор обломков
  (состояния узлов), наклейки копоти.

### 18.6 Порядок работ

1. Паспорт и раскладка: переезд всех моделей скриптом, генераторы и редактор пишут и читают новую раскладку.
2. Экран 1 под закладки вариантов, секции «Сборка / Скорлупа», скорлупа пишется в `<вариант>/shell/`.
3. Варианты повреждений в генераторе; поиск повторов.
