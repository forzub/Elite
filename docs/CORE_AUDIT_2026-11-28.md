## 1. Главные выводы

1. **У D-2 найдена детерминированная причина** [подтв.]. Голодные тики возникают не случайно, они заложены в
   конструкцию:
   - клиент выпускает команды не больше чем на 0,05 с за кадр (`SpaceState.cpp:2225`);
   - сервер за кадр принимает до 0,25 с плюс долг 0,5 с и до 8 шагов (`ServerRunner.h:19-21`).

   Поэтому каждый кадр длиннее 50 мс даёт тики сервера без команды. С собственными часами сервера то же самое
   бывает и при 60 FPS: команды приходят пачками по кадрам, буфера против джиттера нет. Вероятно, отсюда и
   «раскачка» в режиме собственных часов. D-2 и D-4 — один корень: темп выпуска команд не связан с темпом их
   потребления, и у клиента с сервером разные базы времени.
2. **Правило физического управления (§2 решений) нарушается в шести местах** (раздел 4). Два из них — сервисы
   посадки и стыковки, их исправление автор отложил. Ещё четыре — в самом полёте (ориентация в J-полёте, отмена
   прыжка, взлёт); это ядро.
3. **Математика преобразований верна** (`KinematicFrame`, `ShipReferenceFrameSnapshot`, мост карты хаба). Ошибки —
   в местах вызова:
   - скорость переводится без переносной скорости системы отсчёта;
   - смена системы отсчёта идёт через API спавна;
   - движение в орбитальной системе хаба интегрируется без фиктивных сил [подтв.].
4. **D-5 шире, чем описано.** Нет единого способа прочитать «состояние симуляции на сейчас»:
   - `transform` своего корабля — это уже предсказание, записанное поверх снапшота;
   - решения посадки идут через вспомогательную функцию отрисовки, которую тест не видит;
   - пилот строя шагает по настенным часам кадра.
5. **Обработка команд:** NaN проходит в авторитетное состояние; локальный клиент передаёт поля, которых нет в
   протоколе TCP; при переполнении очереди теряются разовые события.
6. Сервер шагает строго фиксированным шагом, физика сервера от FPS не зависит. От FPS зависят:
   - количество команд, то есть ввод (п. 1);
   - клиентские таймеры и пилот строя (T-3…T-6);
   - время сервера в режиме по умолчанию (D-4).

## 5. Уточнённая программа стабилизации

Порядок шагов — утверждённый автором (§7). Состав каждого шага уточнён находками; новых подсистем нет. Каждый шаг
начинается с поведенческого теста, который сейчас красный.

1. **Документация** — по ревизии и решениям автора. Сюда же пометка F-1 и F-2 как известных отложенных нарушений.
2. **D-1. Системы отсчёта:**
   - одна функция смены системы отсчёта; она сохраняет мировую позицию, скорость, ориентацию, угловую скорость и
     режимы регуляторов (на базе `handOverToHub`), а `placeShipInReferenceFrame` остаётся только для спавна;
   - скорость везде переводится через `worldToLocalVelocity` (F-7, F-10, F-11, F-12);
   - фиктивные силы при интегрировании в орбитальной системе хаба (F-8);
   - **Тест:** мировое состояние инвариантно при смене системы отсчёта; свободный дрейф в орбитальной системе
     совпадает с интегрированием в инерциальной.
3. **D-5. Управление и отрисовка:**
   - один способ чтения состояния симуляции на сейчас (P-7), отдельно от предсказанной копии для отрисовки (R-4);
   - перевод потребителей P-1…P-5 и P-8;
   - один и тот же базис для всех векторов (P-3);
   - **Тест:** команды и маршрут одинаковы при разной силе сглаживания отрисовки.
4. **D-2 и D-3. Команды и предсказание:**
   - **Сначала замер:** трасса `[InputQueue]` показывает голодные тики при 30, 60 и 144 FPS и с собственными часами.
   - **Затем исправление:**
     - согласованный темп выпуска команд и буфер против джиттера (T-1, R-2);
     - соответствие «квитанция ↔ тик» в снапшоте (R-1);
     - один горизонт предсказания для позиции и ориентации (R-3);
     - проверка входа: конечность, диапазоны, скачок номера (R-8);
     - одинаковые поля команды в локальном режиме и по TCP (R-7);
     - `controlEpoch` в команде (R-11);
     - разовые поля не повторяются на голодном тике (R-9);
     - тик происхождения у строк частичного снапшота (R-5);
     - единый штамп блока сессии (R-6);
     - защита от отсутствия своей строки (R-10).
   - **Тест:** при пропусках и пачках команд ошибка предсказания не растёт.
5. **D-4. Время:**
   - собственные часы сервера по умолчанию, одна база времени (T-2);
   - задержка петли — в настенном времени (T-8);
   - клиентские пилоты и таймауты — на серверном времени (T-3…T-6);
   - отдельные часы стройки у сервера и клиента (T-7);
   - затем снять обходы, маскировавшие D-4: слои B4 и подгонку кадра при свёрнутом окне;
   - **Прогоны:** TCP, потеря фокуса, свёрнутое окно, долгий кадр, пауза с долгом.
   - **Тест:** состояние после N секунд симуляции не зависит от FPS клиента.
6. **D-6. Тесты:**
   - подключить C++ контрактные наборы к `run_gates`;
   - удалить и переписать проверки по ревизии §4, включая проверки интерфейса старого Model Asset Editor; проверки
     формата `src/model_asset` сохраняются;
   - переписать `check_navigation_foundation_lock` по функциям (P-6);
   - исправить список известных красных.
7. **D-7** — сохранить диагностику зависания; исследовать, если воспроизведётся.
8. **Итоговая проверка** по критериям §8, отчёт, контрольная ревизия для независимого аудита.

F-3…F-6 (ориентация и скорость в J-полёте, при отмене прыжка и при взлёте) входят в шаг 2 после ответа автора на
вопрос 1. F-6 — без вопроса.

**Не входят** (решения автора §6):
- F-1 и F-2 (сервисы посадки и стыковки);
- T-10 и всё, что касается планировщика;
- пилот строя — только перевод на серверное время и состояние симуляции (минимум для критериев FPS и сглаживания);
  его поведение не настраивается.
